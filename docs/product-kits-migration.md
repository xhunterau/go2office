# go2_kits 迁移 + 商品套装（Kit）功能 — 开发文档

> 状态：**已实现并在远端库执行完成**（2026-07-25）
> 创建日期：2026-07-25
> 前置文档：`docs/products-domain-migration.md`（products/brands/suppliers/origins 已迁移完成）
> 后续文档：`docs/product-kit-pricing.md`（2026-07-29）—— 基于本表的成本卷积与派生属性。本文 §2 记录的三项数据现状（空套装、无嵌套、`qty` 分布）在那里直接决定了实现细节，其中「空套装」数已由 23 增至 **24**。

## 1. 目标

1. 将 Laravel 遗留表 `go2_kits`（商品套装组成明细）迁移为正式表 `public.product_kit_items`。
2. 提供**幂等**的数据搬运脚本 `scripts/migration/002_product_kits_data.sql`，可在最终 Laravel 备份导入 `go2_kits` 后重复执行完成同步。
3. 落地商品详情页 `Kit Components` tab 的完整 CRUD，替换当前的 `ProductPlaceholderPanel` 占位面板。

## 2. 现状核查（2026-07-25 连接远端库 `nszriuqpumbyigxwtccs` 实测）

源表结构（无任何 DB 级约束，与其他 `go2_*` 表一致）：

| 列 | 类型 | 可空 |
|---|---|---|
| `id` | bigint | NO |
| `kit_id` | bigint | NO |
| `product_id` | bigint | NO |
| `qty` | integer | NO |
| `created_at` | timestamp without time zone | YES |
| `updated_at` | timestamp without time zone | YES |

语义：`kit_id` → 套装商品（`go2_products.id`），`product_id` → 组件商品（`go2_products.id`），`qty` → 该组件在套装中的数量。**没有独立的 "kits" 主表**，套装本身就是一条 `go2_products` 记录（`is_kit = 1`）。

数据质量（699 行，`id` 范围 1–708）：

- `kit_id` 孤儿引用 **0**，`product_id` 孤儿引用 **0**
- 两侧引用的商品**均未软删除**（`deleted_at IS NULL`），因此不与"只迁移未软删除商品"的既有决策冲突
- `kit_id` 指向的商品 **100% 为 `is_kit = 1`**
- 组件商品**无一个是套装**（不存在嵌套套装）
- 无自引用（`kit_id = product_id` 为 0 行）
- `(kit_id, product_id)` **无重复组合**
- `qty` 取值 1–100，全为正整数
- `created_at` / `updated_at` 无空值，范围 2020-03-29 ~ 2025-09-16；66 行两个时间戳不相等（存在过更新）
- 明细行数分布：1 行 577 个套装、2 行 17、3 行 8、4 行 11、5 行 1、6 行 1、9 行 1
- **616 个套装有明细，但 `is_kit = 1` 的未删除商品共 639 个 → 23 个"空套装"**（打了标记却无任何组件行）

## 3. 已与用户确认的关键决策

| 决策点 | 结论 |
|---|---|
| 表名 | `public.product_kit_items` |
| 列命名 | 语义化：`kit_product_id` / `component_product_id` / `qty`（不沿用 `kit_id`/`product_id`，避免被误读为指向某张独立 kits 表） |
| 主键策略 | 沿用 bigint 自增主键，**直接等于旧 `go2_kits.id`**（与 products 域一致，`ON CONFLICT (id)` 天然完成新旧映射，无需 mapping 表） |
| 约束强度 | PK + 两个 FK + `UNIQUE (kit_product_id, component_product_id)` + `CHECK (qty > 0)` + `CHECK (kit_product_id <> component_product_id)`。**不**用触发器强制 `is_kit` 一致性、**不**禁止嵌套套装 |
| `products.is_kit` 联动 | **保持独立**：`is_kit` 仍是商品表单里的人工开关，增删组件行不自动改写它 |
| 23 个空套装 | 原样保留，视为"已标记为套装但尚未录明细"的合法中间状态；UI 显示空状态提示 |
| 本轮范围 | 迁移层（schema + 数据脚本）+ `Kit Components` tab 完整 CRUD |

## 4. 待确认的默认取值（如无异议按此实现）

| 项 | 默认做法 | 理由 |
|---|---|---|
| `kit_product_id` 的 FK 删除行为 | `ON DELETE CASCADE` | 套装商品被删除时，其明细行失去意义，随之清理 |
| `component_product_id` 的 FK 删除行为 | `ON DELETE RESTRICT` | 某商品仍是别人的套装组件时，禁止误删该商品；由 UI 给出明确报错 |
| `created_at` | 迁移旧值（按 `Australia/Sydney` 解读后转 `timestamptz`） | 与 products 迁移的时区处理一致 |
| `updated_at` | 建 `moddatetime` 触发器自动维护；首次插入时写入旧值 | 沿用 `20260719150000_add_products_timestamps_trigger.sql` 的既有模式（commit `acae529`：时间戳交由数据库 trigger 维护）。**注意**：`moddatetime` 在任何 UPDATE 上都会把 `updated_at` 覆盖为 `now()`，所以脚本**重跑时被更新的行**无法保留旧 `updated_at`——这是既有 trigger 的固有行为，不是本次引入的缺陷 |
| 组件行排序 | 按 `component_product_id` 排序展示（源表无排序列，不新增 `sort_order`） | 源数据没有顺序语义，避免凭空造字段 |

## 5. Schema 迁移设计

文件：`supabase/migrations/20260725110000_create_product_kit_items.sql`（按规则 14 包 `BEGIN` / `COMMIT`）

```
CREATE TABLE public.product_kit_items (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  kit_product_id bigint NOT NULL REFERENCES public.products (id) ON DELETE CASCADE,
  component_product_id bigint NOT NULL REFERENCES public.products (id) ON DELETE RESTRICT,
  qty integer NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT product_kit_items_qty_positive CHECK (qty > 0),
  CONSTRAINT product_kit_items_no_self_reference CHECK (kit_product_id <> component_product_id),
  CONSTRAINT product_kit_items_unique_component UNIQUE (kit_product_id, component_product_id)
);
```

- 索引：`component_product_id` 单列索引（用于"该商品被哪些套装引用"的反查）。`kit_product_id` 已是 UNIQUE 约束的前导列，无需再建。
- 触发器：`product_kit_items_set_updated_at`（`extensions.moddatetime (updated_at)`）。
- RLS：`ENABLE ROW LEVEL SECURITY` + 策略 `authenticated_full_access`（`FOR ALL TO authenticated USING (true) WITH CHECK (true)`）+ 显式 `GRANT SELECT, INSERT, UPDATE, DELETE TO authenticated`——与既有 4 张表完全一致（`config.toml` 未开 `auto_expose_new_tables`）。

## 6. 数据搬运脚本设计

文件：`scripts/migration/002_product_kits_data.sql`

- 单条 `INSERT ... SELECT ... FROM public.go2_kits ... ON CONFLICT (id) DO UPDATE SET ...`，幂等。
- **显式列出目标列**，不使用 `SELECT *`（规则 15）。
- 防御性过滤：只搬运两侧商品都已存在于 `public.products` 的行（用 `EXISTS` 判断）。当前实测应过滤掉 0 行；此过滤是为最终同步兜底——若届时 Laravel 侧新增了指向软删除商品的明细行，脚本会跳过而非因 FK 冲突整体回滚。
- 脚本尾部保留一段**注释形式的诊断查询**，用于人工确认本次被跳过的行数与具体 id。
- 结尾 `setval` 把 `product_kit_items` 的 id 序列推到 `max(id) + 1`，避免应用新建行与迁移行 id 冲突。
- **规则 15 需扩展**：CLAUDE.md 第 15 条目前只点名 `001_products_domain_data.sql`，本次需把 `002_product_kits_data.sql` 及 `product_kit_items` 表纳入同步约束范围（同一次改动中更新 CLAUDE.md）。

## 7. UI / 应用层设计（Kit Components tab）

### 7.1 数据读取

- `src/lib/queries/product-kit-items.ts`
  - `fetchProductKitItems(supabase, kitProductId)`：查 `product_kit_items` 并 join 组件商品的 `id, sku, name, image_url, purchase_price, retail_price, currency, is_active`，按 `component_product_id` 排序。
  - `searchProductsForKit(supabase, kitProductId, keyword)`：为"添加组件"选择器提供候选商品，按 `sku`/`name` 模糊匹配，排除自身与已在明细中的商品，限制返回条数（20）。

### 7.3 校验与 Server Actions

- `src/lib/validations/product-kit-item.ts`：Zod schema

- 唯一约束冲突（重复组件）需捕获 Postgres `23505`，返回可读错误 "This product is already a component of this kit."；`23514`（CHECK）返回相应提示。
- Toast 反馈用 `sonner`（规则 7）。

## 10. 风险与注意事项

- 本次是第一次给这批明细数据加上真正的约束（PK/FK/UNIQUE/CHECK）。当前数据 100% 满足，但若 Laravel 停用前又产生了违规数据（重复组件、`qty <= 0`、自引用、指向软删除商品），最终同步时会报冲突或被跳过，需人工介入。
- 按决策 `is_kit` 与明细行**不联动**，因此可能出现两类不一致状态：`is_kit = true` 但无明细（当前 23 个），以及 `is_kit = false` 却有明细（当前 0 个，但 DB 层不阻止）。后者会导致 `Kit Components` tab 因 `showKitTab = product.is_kit` 而**不显示**、明细被隐藏。建议在商品列表/详情后续迭代中增加一处数据体检视图，而不是靠约束堵。
- 组件商品 FK 为 `RESTRICT`，意味着删除商品时可能被套装明细挡住。商品删除功能上线时需要给出清晰错误提示（当前商品域尚无删除入口）。
- 不支持嵌套套装（DB 层不禁止，但 UI 与后续 BOM 展开逻辑均按单层假设实现）。若日后业务需要多层套装，需重新评估递归展开与循环引用检测。**成本卷积按同一假设实现**：组件本身是套装时整个套装成本输出 NULL 而非静默少算，见 `docs/product-kit-pricing.md` §4.5。
- `go2_kits` 临时表在最后一次导入并核对完成后可随其他 `go2_*` 表一并清理，脚本 002 随之退休（同规则 15 的脚本退休条款）。
